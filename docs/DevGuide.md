# Bari's Room — Development Guide

## 1. 프로젝트 목적

Bari's Room은 일반적인 포트폴리오나 메뉴형 홈페이지가 아니다.

방문자가 픽셀 공간 안을 직접 이동하고, 방 안의 오브젝트를 사용하며 바리의 취향과 기록을 발견하는 **디지털 생활 공간**이다.

핵심 감각:

- 웹페이지를 보고 있다는 느낌보다 누군가의 공간을 구경하는 느낌
- 메뉴를 누르는 대신 공간을 걸어 다니며 발견하는 경험
- 완성된 전시장이 아니라 시간이 쌓이며 성장하는 작업실
- 현실과 판타지의 중간에 있는 따뜻하고 아늑한 공간

## 2. 기술 방향

- Frontend 중심
- PixiJS 기반 2D 픽셀 월드
- 초기 버전은 백엔드 없이 시작
- 필요할 때 Serverless Function과 데이터 저장 구조를 단계적으로 추가
- 초기 구현은 명확한 2D 장면 연결을 우선하며 3D 시점은 사용하지 않음

## 3. 화면과 카메라

### 최신 확정 방향

- 방 전체를 한 화면에 모두 보여주지 않는다.
- 플레이어 주변의 일부 공간만 화면에 보인다.
- 플레이어가 이동하면서 방을 탐색한다.
- 플레이어는 화면에서 큼직하게 보여야 한다.
- 플레이어의 화면상 표시 높이는 **viewport 높이의 약 40%**를 목표로 한다.
- 화면 크기와 종횡비가 달라도 캐릭터의 체감 크기가 크게 흔들리지 않게 한다.

### 구현 원칙

월드 좌표와 화면 좌표를 분리한다.

권장 구조:

```text
App / Renderer
└── World Container
    ├── Background Layer
    ├── Object Layer
    ├── Player Visual
    ├── Foreground Layer
    └── Effects Layer
```

카메라는 `World Container`의 위치 또는 별도 Camera 클래스로 관리한다.

카메라 관련 값:

- viewport size
- world size
- camera position
- camera target
- camera bounds
- optional smoothing
- resize recalculation

초기에는 과도한 흔들림, 줌 연출, 복잡한 시네마틱 카메라를 넣지 않는다.

## 4. 플레이어 스케일

### 화면상 목표

```text
displayHeight ≈ viewportHeight × 0.4
```

이 값은 **렌더링 목표 크기**다. 월드 물리 크기나 충돌 크기를 뜻하지 않는다.

### 반드시 분리할 것

1. **Visual bounds**
   - 화면에 보이는 캐릭터 전체
   - 머리카락, 리본, 옷자락 포함

2. **Collision bounds**
   - 벽과 가구에 부딪히는 영역
   - 발 주변의 작은 사각형 또는 캡슐형 영역 권장

3. **Interaction origin**
   - 상호작용 거리 계산의 기준점
   - 발 중앙 또는 몸 중심 하단 권장

4. **Sort anchor**
   - Y-sort 기준점
   - 캐릭터 발바닥 위치 권장

### 픽셀 스프라이트 적용 시

- 원본 픽셀 크기와 화면 표시 크기를 분리한다.
- nearest-neighbor 렌더링을 유지한다.
- 가능하면 정수 배율을 우선하되, 반응형 목표를 심하게 해치지 않는 범위에서 선택한다.
- 스프라이트 교체가 이동·충돌·상호작용 로직에 영향을 주지 않아야 한다.

## 5. 월드 스케일

- 모든 제작은 타일을 기준으로 한다.
- 캐릭터를 기준 단위로 오브젝트 크기를 정한다.
- 현실 치수보다 캐릭터와의 관계, 화면 가독성, 연출 목적이 우선이다.
- 문·책상·의자·침대처럼 캐릭터가 직접 사용하는 물건은 신체 관계가 자연스러워야 한다.
- 책·컵·화분·컴퓨터·스위치처럼 작은 기능성 오브젝트는 알아보기 쉽게 조금 크게 표현할 수 있다.
- 창문·벽난로·수족관·대형 책장처럼 분위기를 만드는 요소는 연출을 위해 과장할 수 있다.
- 큰 캐릭터 화면 구성에 맞춰 가구와 통로도 큼직하게 재설계한다.

## 6. 이동과 충돌

- 이동 속도는 화면 픽셀이 아니라 월드 단위와 delta time을 기준으로 한다.
- 화면 리사이즈가 이동 속도를 바꾸면 안 된다.
- 충돌은 렌더링 사각형 전체가 아닌 발 영역을 사용한다.
- 가구 뒤를 지나갈 수 있는 깊이 표현이 필요하면 Y-sort 또는 foreground mask를 사용한다.
- 상호작용 가능한 오브젝트 앞에는 자연스럽게 접근할 공간을 확보한다.
- 점프는 문서상 v0.1 범위지만, 공간 탐색에 실질적으로 필요한지 구현 전에 다시 검토한다.

## 7. 오브젝트 상호작용

사용자는 UI를 조작하는 것이 아니라 **세계 속 오브젝트를 사용한다**고 느껴야 한다.

예시:

- 컴퓨터 → 프로젝트 허브
- 개발일지 → 현재 작업
- 책장 → 완료된 기록
- 게시판 → 최근 업데이트
- 문 → 다른 공간
- 스위치 → 실내조명 ON/OFF

원칙:

- 오브젝트 의미와 결과가 일치해야 한다.
- 중요한 기능은 처음 방문한 사람도 발견할 수 있어야 한다.
- 모든 장식에 기능을 억지로 넣지 않는다.
- Hover는 작고 명확하게, Click은 즉각적으로 반응한다.
- 오브젝트가 먼저 움직인 뒤 콘텐츠가 열린다.
- 반복 입력으로 상태가 망가지지 않게 한다.

## 8. 아트 및 연출

- Mid Resolution Pixel Art
- Quiet · Cozy · Night · Warm Light
- Modern Cozy 70% + Natural Cozy 30%
- 낮은 채도, 어두운 네이비, 블루그레이, 월넛 브라운, 따뜻한 앰버
- 순수 검정 외곽선 금지
- 기본 3단계 명암
- 공간의 분위기는 오브젝트 명암보다 환경광과 조명으로 만든다.
- 화려한 파티클, 화면 흔들림, 과도한 바운스는 지양한다.
- 캐릭터보다 공간의 잔잔한 움직임이 중심이다.

## 9. 반응형 정책

리사이즈 시 다음을 함께 재계산한다.

- renderer / canvas size
- player display scale
- camera viewport
- camera bounds
- player screen placement
- interaction UI placement
- pixel snapping 필요 여부

리사이즈 뒤에도 다음 상태가 보존되어야 한다.

- 플레이어 월드 좌표
- 현재 방
- 조명 상태
- 상호작용 상태
- 이동 입력 상태의 안전한 해제

## 10. 코드 품질 기준

- TypeScript 타입을 명확히 사용한다.
- 매직 넘버는 설정값으로 분리한다.
- 플레이어 40% 값은 예: `PLAYER_VIEWPORT_HEIGHT_RATIO = 0.4`로 관리한다.
- 단일 클래스가 입력, 이동, 렌더링, 충돌, 카메라를 모두 책임지지 않게 한다.
- 임시 Graphics와 실제 Sprite가 공통 인터페이스를 사용하도록 설계한다.
- 새 시스템은 교체 가능하고 테스트 가능한 작은 단위로 분리한다.
